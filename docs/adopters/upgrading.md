# Upgrading

> **Status:** DEVAI 3.0.0 is in development; this page describes the specified behaviour (docs/framework). Commands are not yet published.

Two things change under a running product: the DEVAI version and the specs. In both cases DEVAI
does not migrate anything for you. It checks that every generated byte can still be reproduced, and
it tells you which command restores that.

## What a generated module records

Every module the generator writes has a `domain/<m>/generation-manifest.json`
([02 §7](../framework/02-architecture.md), [09 §2](../framework/09-rail.md)):

- `generatorVersion`, the DEVAI package version that rendered it;
- `specId`, `specSha256` (over the spec file) and `machineBlockSha256` (over its fenced YAML);
- the `options` used (`web`, `locales`, `lgpd`, `productPrefix`);
- every file with its digest and its mode, `generated` or `seed`.

It has no timestamp: identical inputs give identical bytes. Only a `generate` packet may change it
(PL-07) ([02 §7](../framework/02-architecture.md), [05 §5](../framework/05-task-packet.md)).

## How `generated` verifies a module

On pre-push and on the PR, the `generated` node re-renders each module in memory from the
**recorded** spec bytes and options, and compares the bytes and the file set
([08 B.16](../framework/08-cli-and-nodes.md), [09 §3](../framework/09-rail.md)). Three outcomes
matter when you upgrade:

| Situation | Result | Remedy printed |
|---|---|---|
| Installed CLI version ≠ the manifest's `generatorVersion` | `UNKNOWN: generator-version-mismatch` | `pnpm add -D @devai-nyx/cli@<version>` |
| A generated file was edited by hand | `FAIL … differs from regeneration [S-45]` | regenerate (`devai new module --regenerate`) or move the logic to a seed file |
| The recorded spec bytes cannot be found | `UNKNOWN: generator-unavailable` | regenerate in a generate packet |

A spec that has since been superseded never fails `generated`: old pins stand
([08 B.16](../framework/08-cli-and-nodes.md), [D-053](../../decisions.md)). This is why the DEVAI
packages are pinned exactly, never by range ([09 §3](../framework/09-rail.md); 12 §3).

## Regenerating a module

```sh
devai new module --spec <path-to-the-same-spec> --regenerate
```

Run it inside a `generate` packet, since it rewrites the manifest. For each manifest entry
([08 A.2](../framework/08-cli-and-nodes.md)):

- `generated` files are rewritten;
- `seed` files are never written; each is reported as `seed unchanged, safe to overwrite` or
  `seed edited, left alone`;
- module SQL already present at the merge base is never rewritten (D-033, LINT013).

There is no three-way merge assistant ([D-033](../../decisions.md)). If a seed you edited needs the
new shape, you change it yourself, in a `code` or `fix` packet.

`--regenerate` against a different spec id exits 1 `spec-mismatch`, unless that spec is a successor
whose `supersedes.id` equals the manifest's `specId` ([08 A.2](../framework/08-cli-and-nodes.md)).

## Changing a spec: successor specs

An approved spec does not change. A change of even one byte is a **successor spec**
([D-053](../../decisions.md), [06 §6](../framework/06-spec-format.md),
[05 §4](../framework/05-task-packet.md)):

1. The successor carries `supersedes: {id, path, sha256}`, naming the predecessor's approved bytes.
2. The predecessor receives exactly one more edit: its status line becomes
   `superseded-by: <SpecId>`. `spec-lint` SL09 checks that the pair agrees.
3. New packets pin the successor. A new packet may not pin a spec whose HEAD carries
   `superseded-by` (PL-04).
4. Old packets are unaffected: they hash the spec at their own `base` and still accept against it.

To bring a generated module to the successor, regenerate inside a `generate` packet
([09 §3](../framework/09-rail.md)). Non-SQL generated files and the manifest follow the successor.
Base-present SQL stays untouched. If the `data` block changed, the generator prints
`write domain/<slug>/db/<ns>_<slug>_<nn>_<topic>.sql by hand and append it to database/seed/modules.txt`,
and `sql-typed`'s database part fails until that migration exists. Editing the old SQL file instead
is a LINT013 failure ([D-043](../../decisions.md)). Controller drift against the new routes is
reported by `route-contract` ([02 §7](../framework/02-architecture.md)).

A business decision that changes what acceptance means takes the same path: `product/` edit, a
`spec` packet, a successor spec, then new packets ([05 §4](../framework/05-task-packet.md),
[D-035](../../decisions.md)).

## What the law does not prescribe

The checks above are specified, but there is no "upgrade" command or procedure:

- DEVAI's own release notes and compatibility policy for 3.x are not part of the law.
- Each module's `api/package.json` is a seed whose `@devai-nyx/decorators` dependency starts exact at
  `generatorVersion` ([09 §2](../framework/09-rail.md)). Seeds are hand-owned, so `--regenerate`
  does not bump it.
- STYNX packages are pinned to one exact fixed-group version (12 §3). The law does not say how a
  product moves to a later one.

When one of these comes up, record the choice in your repository's `decisions.md`
([D-031](../../decisions.md)).
